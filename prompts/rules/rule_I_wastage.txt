RULE I — WASTAGE TABLE: DEFINITIONS, JOINS, AND VARIANTS

— Wastage Column Definitions —
TABLE: itciot.wastage_records
Differentiate carefully between these columns:
- "wastage" or "total wastage" → wastage_kg  (NUMERIC: physical weight in kg)
- "rejected bags count" or "failed bags" → failed_bag_rejection  (NUMERIC: COUNT of bags, NOT a weight)
- "rejection kg" or "manual rejection" → manual_rejection_kg  (NUMERIC: weight in kg)
- "filled bag rejection" → filled_bag_rejection  (NUMERIC: weight in kg)
NEVER use failed_bag_rejection as a weight. It is a count.

— Wastage JSON Text Cast —
TABLE: itciot.wastage_records
Columns wastage_breakdown and unaccounted_downtime_breakdown are stored as TEXT, NOT JSONB.
You MUST cast them before using JSON functions:
  jsonb_array_elements(wastage_breakdown::jsonb)

— Forbidden Join: employees_list —
Do NOT join employees_list in any query — the table currently has 0 rows and will silently produce empty results.
When users ask about operators, shift in-charges, or JTAs:
Query the columns operator_name, jta_name, and shift_incharge_name directly from wastage_records.

— Variants vs Flavours —
Product variants ('Flat Cut', 'Ridge Cut', etc.) are mapped differently:
  - ega_details_data → use the variant column
  - oee_details_data → use the variant column
  - production_speed_details_data → use the variant column
  - wastage_records → use the flavour column  (there is NO variant column in wastage_records)
When filtering wastage by product type, use: WHERE flavour ILIKE '%Flat Cut%'
